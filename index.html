Agentic Teams On BYOK And Repos (ATOBAR)

ATOBAR (Agentic Teams On BYOK And Repos) is a Hub-and-Spoke software factory built around GitHub. Co-founders and collaborators bring their own KMS-encrypted LLM API keys (BYOK), route costs and models per repository and per role today ([AS-BUILT]) with per-invoking-user billing and profile default keys next ([VISION]), coordinate strictly through GitHub Jumbo Issues and Pull Requests, and let isolated AWS EC2 Spot roles (PLANNER → DEVELOPER → EVALUATOR → ARBITRATOR) write, visually verify in X11, and squash-merge code with a one-commit exit.

Fully Forkable for Any Use-Case: ATOBAR is 100% open-source (MIT) and domain-neutral. You can fork the monorepo, connect your own GitHub App, database, and cloud account, and adapt the roles or verification checks for any workflow: building web and mobile apps, automating internal company tools, running security or compliance fixes, maintaining data pipelines, or keeping documentation in sync with code.

Explicit Anti-Goals: What ATOBAR Refuses to Build

[ARCHITECTURAL INVARIANTS]
ANTI-GOAL 1

No Custom IDE or Proprietary Chat App

All human planning and code review happen in GitHub Issues and Pull Requests. Collaborators plan in Jumbo Issues, inspect visual screenshots in PRs, and steer active runs with @atobar-flow-agent comments.

ANTI-GOAL 2

No Atobar SDK Inside Client Repos

Client repositories never import atobar-flow packages at runtime. Only two standard GitHub Actions YAML files live in .github/workflows/, guaranteeing a 1-commit exit at any time.

ANTI-GOAL 3

No LLM in Merge or Budget Decisions

State machine transitions (step()), circuit breakers, Spec-Sufficiency checks, and metric gate merges (arbitrate()) are 100% deterministic Python.

J3: Long-Running Execution, Warm Handover & Plain-English PR Steering

On approval (flow:approved or @atobar-flow-agent approve), CONDUCTOR launches an EC2 Spot VM. PLANNER → DEVELOPER transitions and rework turns reuse the warm Spot VM inside isolated git worktree directories (prepare_role_worktree() in flow-agent/src/flow_agent/runtime/sandbox.py) via POST /v1/runs/{run_id}/turn-complete (J3.1).

Verifying roles (EVALUATOR, ARBITRATOR) never accept a warm handover from DEVELOPER: WARM_HANDOVER_FORBIDDEN_ROLES = {"evaluator", "arbitrator"} (contracts/src/atobar_contracts/conductor_io.py, J43) terminates the warm developer VM and forces a fresh Spot VM launch for QA (J3.2). Throughout execution, live tool calls, heartbeats, and spend stream into the pinned GitHub telemetry comment, and collaborators steer active or escalated PRs using @atobar-flow-agent comments (J3.3, J49).

Onboard a Client Repository in 5 Minutes (J1.1–J1.4)

Run onboard.sh inside any git repository clone where you have GitHub admin permissions. The script verifies prerequisites (git, gh, curl), guides you through installing the atobar-flow-agent GitHub App, saves your repository's ATOBAR_TENANT_TOKEN secret, and opens the onboarding pull request.

$curl -fsSL https://raw.githubusercontent.com/atobar-flow/atobar-flow/main/scripts/onboard.sh | bash
  1. STEP J1.1: GITHUB APP & TOKEN [AS-BUILT]

    Install the atobar-flow-agent GitHub App on your client repo and save ATOBAR_TENANT_TOKEN via gh secret set.

  2. STEP J1.2: KMS BYOK & PER-ROLE ROUTING [AS-BUILT]

    Save your provider API keys (claude, gemini, openai, deepseek, grok) in the KMS AES-GCM vault and bind models per role in tenant_role_llm.

  3. STEP J1.3: PER-INVOKING-USER & PROFILE DEFAULT KEYS [VISION]

    Collaborators attach personal repo keys or a Default Profile Key (/profile) so every run bills the invoking GitHub user.

  4. STEP J1.4: SOTAWIKI & 2-FILE PR [AS-BUILT]

    The onboarder Spot role synthesizes your initial Mermaid SotaWiki and opens a PR with flow-trigger.yml and flow-metrics.yml.
